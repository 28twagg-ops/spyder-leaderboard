## Adaptive budget policy (initial planning heuristics, not billing limits)
For each pool independently, compute remaining allowance and remaining days until reset using the actual dashboard units. Retain 15–20% of initial allowance for difficult fixes and final reviews. Allocate spend by priority and task risk; avoid exhausting a pool merely because the other is available. For the third-party pool, starting allocation: 25% architecture/design, 30% core development and review, 25% independent evidence/safety review, 20% reserve. Adapt once the first few work batches show actual usage. For Cursor pool: routine implementation, validation and docs first, retain reserve. If remaining allowance is above 50%, proceed with planned batches; 20–50%, prefer efficient explicit models and prioritize core features; below 20%, preserve the remaining premium capacity for critical audits/fixes, checkpoint or use the other included pool if it has capacity; at exhaustion, stop tasks that would exceed allowance, and continue only with genuinely available included usage or owner-authorized work. These are percentage-of-initial-pool triggers, not automatic charges. Adjust for time to reset and task dependency. Do not auto-run or schedule work at reset.
Estimate the next batch in the billing units where possible (input, output, cache-read/write and context-tier prices differ); use measured dashboard deltas when available, not invented precision or a fixed token-to-dollar ratio. Record the estimate and actual usage or unknown. Ask owner before a batch likely to consume reserve or exceed allowance.
